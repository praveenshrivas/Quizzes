# 1. Identify the CPU Requirements of the Rabbit Pod

## Question

> A Pod called `rabbit` is deployed. Identify the CPU requirements set on the Pod in the current/default namespace.

---

## Command

First, verify that the Pod exists:

```bash
kubectl get pods
```

Expected:

```text
NAME      READY   STATUS    RESTARTS   AGE
rabbit    1/1     Running   0          ...
```

Now describe the Pod:

```bash
kubectl describe pod rabbit
```

Look for:

```text
Requests:
  cpu:     ...
Limits:
  cpu:     ...
```

You can filter the output:

```bash
kubectl describe pod rabbit | grep -i cpu
```

---

## Explanation

A Kubernetes container can have two important CPU resource settings:

```text
Requests
Limits
```

For example:

```text
Requests:
  cpu:     100m
Limits:
  cpu:     200m
```

This means:

* Kubernetes reserves/schedules the Pod based on the CPU request.
* The container cannot normally use more CPU than its CPU limit.

---

## What Does `100m` Mean?

Kubernetes represents CPU using CPU units.

```text
1 CPU = 1000m
```

Therefore:

| CPU Value |  Meaning |
| --------- | -------: |
| `100m`    |  0.1 CPU |
| `250m`    | 0.25 CPU |
| `500m`    |  0.5 CPU |
| `1000m`   |    1 CPU |
| `2000m`   |   2 CPUs |

So:

```text
100m = 0.1 CPU
```

---

## Get CPU Information Using YAML

You can also inspect the complete Pod specification:

```bash
kubectl get pod rabbit -o yaml
```

Look under:

```yaml
resources:
  requests:
    cpu: ...
  limits:
    cpu: ...
```

---

## Get Only the CPU Request

A useful JSONPath command is:

```bash
kubectl get pod rabbit -o jsonpath='{.spec.containers[*].resources.requests.cpu}'
```

---

## Get Only the CPU Limit

```bash
kubectl get pod rabbit -o jsonpath='{.spec.containers[*].resources.limits.cpu}'
```

---

## Important Notes

### CPU Request

The CPU request is primarily used by the **Kubernetes scheduler**.

For example:

```yaml
resources:
  requests:
    cpu: "100m"
```

Kubernetes considers that the Pod needs:

```text
0.1 CPU
```

when deciding whether a node has enough available resources.

### CPU Limit

The CPU limit controls how much CPU the container can consume.

Example:

```yaml
resources:
  limits:
    cpu: "200m"
```

# 2. Delete the Rabbit Pod

## Question

> Delete the `rabbit` Pod.

---

## Command

```bash
kubectl delete pod rabbit
```

Expected:

```text
pod "rabbit" deleted
```

---

## Wait for the Pod to Fully Terminate

Check:

```bash
kubectl get pods
```

You should eventually see that `rabbit` is no longer listed.

You can also check directly:

```bash
kubectl get pod rabbit
```

Eventually:

```text
Error from server (NotFound): pods "rabbit" not found
```

---

## Explanation

The command:

```bash
kubectl delete pod rabbit
```

requests Kubernetes to delete the Pod.

The Pod may briefly go through a termination process before it completely disappears.

---

## Important Concept: Pod vs Deployment

If `rabbit` is an **independent Pod**, deleting it means the Pod will remain deleted.

However, if the Pod was created by a:

* Deployment
* ReplicaSet
* StatefulSet
* DaemonSet

the controller may automatically create another Pod.

For example:

```text
Deployment
    |
    v
ReplicaSet
    |
    v
Pod
```

If you delete the Pod:

```text
Pod deleted
    |
    v
ReplicaSet notices desired replicas are not satisfied
    |
    v
New Pod created
```

Therefore, always determine whether a Pod is managed by a controller.

# 4. Identify the Last State Reason

## Question

> Inspect the `elephant` Pod using `kubectl describe` and identify the `Last State Reason` that explains why the container continues to crash.

---

## Command

```bash
kubectl describe pod elephant
```

Look for the container section.

You may see:

```text
State:          Waiting
  Reason:       CrashLoopBackOff

Last State:     Terminated
  Reason:       OOMKilled
  Exit Code:    137
```

The important field is:

```text
Last State:
  Reason: OOMKilled
```

---

## Expected Reason

For this particular scenario, the expected reason is:

```text
OOMKilled
```

---

## What Does OOMKilled Mean?

`OOM` stands for:

> **Out Of Memory**

`OOMKilled` means the container was terminated because it attempted to use more memory than the memory limit assigned to it.

For example:

```text
Container memory usage = 10Mi
Container memory limit  = 5Mi
```

The container exceeds its allowed memory.

Kubernetes/Linux terminates the process.

Result:

```text
OOMKilled
```

---

## Understanding the Sequence

The situation can be visualized as:

```text
Elephant Pod
     |
     v
Container starts
     |
     v
Application consumes memory
     |
     v
Memory usage exceeds container limit
     |
     v
Container is killed
     |
     v
Container exits
     |
     v
Kubernetes restarts it
     |
     v
Application consumes too much memory again
     |
     v
Container gets killed again
```

This can eventually result in:

```text
CrashLoopBackOff
```

# 7. Recreate the Elephant Pod

## Important Kubernetes Concept

Some fields of an existing Pod are **immutable**.

This means you cannot freely modify them after the Pod has been created.

For a simple Pod, changing resource configuration may require deleting and recreating the Pod.

---

## Method Used in the Lab

After editing:

```bash
vi elephant.yaml
```

you can recreate the Pod using:

```bash
kubectl replace -f elephant.yaml --force
```

This forces replacement of the existing Pod.

---

## What Does `--force` Do?

The command:

```bash
kubectl replace -f elephant.yaml --force
```

effectively performs a delete and recreate operation.

Conceptually:

```text
Existing Pod
     |
     v
Delete
     |
     v
Create new Pod
```

---

## Alternative Method

You can explicitly delete the Pod:

```bash
kubectl delete pod elephant
```

Then recreate it:

```bash
kubectl create -f elephant.yaml
```

However, there can be a timing issue if the old Pod has not completely disappeared yet.

You can verify:

```bash
kubectl get pod elephant
```

Then recreate it after deletion completes.

# 12. Kubernetes Resource Requests vs Limits

This exercise is an excellent opportunity to understand one of the most important Kubernetes concepts.

A container can define:

```yaml
resources:
  requests:
    cpu: "100m"
    memory: "10Mi"

  limits:
    cpu: "500m"
    memory: "20Mi"
```

---

## Requests

Requests tell Kubernetes:

> "I need at least this amount of resources for scheduling purposes."

Example:

```yaml
requests:
  memory: 10Mi
```

The scheduler uses the request when deciding whether a node has enough resources.

---

## Limits

Limits tell Kubernetes:

> "This container should not exceed this resource limit."

Example:

```yaml
limits:
  memory: 20Mi
```

If a container exceeds its memory limit, it can be terminated with:

```text
OOMKilled
```

---

# 13. CPU vs Memory Behavior

CPU and memory behave differently when limits are exceeded.

| Resource | If limit is exceeded      |
| -------- | ------------------------- |
| CPU      | Container is throttled    |
| Memory   | Container can be killed   |
| Memory   | May result in `OOMKilled` |

This distinction is very important in interviews.

---

# 14. Understanding `CrashLoopBackOff`

You may see:

```text
STATUS
CrashLoopBackOff
```

This does **not** necessarily mean that the original reason is `CrashLoopBackOff`.

It means Kubernetes is repeatedly trying to restart a container that keeps failing.

For example:

```text
Application starts
       ↓
Application crashes
       ↓
Container restarts
       ↓
Application crashes
       ↓
Container restarts
       ↓
CrashLoopBackOff
```

The actual reason for the previous termination could be:

```text
OOMKilled
```

or:

```text
Error
```

or another termination reason.

Therefore, use:

```bash
kubectl describe pod elephant
```

and inspect:

```text
Last State:
  Reason:
```

---

# 15. `Last State` vs Current `State`

This is another important interview concept.

You may see:

```text
State:          Waiting
  Reason:       CrashLoopBackOff

Last State:     Terminated
  Reason:       OOMKilled
```

These two fields are different.

| Field        | Meaning                                  |
| ------------ | ---------------------------------------- |
| `State`      | Current state of the container           |
| `Last State` | State of the previous container instance |
| `Reason`     | Explanation for the state                |

In this scenario:

```text
Current State:
Waiting
```

because Kubernetes is waiting before restarting the container.

But:

```text
Last State:
Terminated
```

because the previous container instance was terminated.

And:

```text
Last State Reason:
OOMKilled
```

because it exceeded the memory limit.

# 16. Pod Lifecycle States

A Pod commonly goes through states such as:

```text
Pending
Running
Succeeded
Failed
Unknown
```

---

## Pending

The Pod has been accepted by Kubernetes but is not yet fully running.

Possible causes:

* Scheduling problems
* Insufficient CPU
* Insufficient memory
* Node affinity mismatch
* Taints
* Image pulling issues

---

## Running

The Pod has been scheduled and at least one container is running or starting.

---

## Succeeded

All containers have successfully terminated and will not be restarted.

Common for:

* Jobs
* Batch workloads

---

## Failed

All containers have terminated and at least one container failed.

# 18. Why `kubectl describe` Is Important

When troubleshooting Kubernetes, one of the first commands you should know is:

```bash
kubectl describe pod <pod-name>
```

It provides information that is not immediately visible with:

```bash
kubectl get pods
```

For example:

```text
kubectl get pods
```

might only show:

```text
NAME       READY   STATUS             RESTARTS
elephant   0/1     CrashLoopBackOff   5
```

But:

```bash
kubectl describe pod elephant
```

can reveal:

```text
Last State:
  Terminated
  Reason: OOMKilled
  Exit Code: 137
```

This tells us **why** the container is failing.

# 19. Understanding Exit Code 137

You may see:

```text
Exit Code: 137
```

This is commonly associated with a process being terminated by:

```text
SIGKILL
```

In a Kubernetes memory-limit scenario, this often accompanies:

```text
Reason: OOMKilled
```

Therefore, when troubleshooting:

```text
CrashLoopBackOff
```

and you see:

```text
Last State:
  Terminated
  Reason: OOMKilled
  Exit Code: 137
```

you should investigate the container's memory usage and memory limit.

# 20. Common Errors

## Error 1 – Typing the Wrong Pod Name

Your history shows:

```bash
kubectl describe pod rabbot
```

but the actual Pod is:

```text
rabbit
```

Correct:

```bash
kubectl describe pod rabbit
```

Kubernetes object names must match exactly.

---

# Error 2 – Using `grep cpu` Incorrectly

This command:

```bash
kubectl describe pod rabbit | cpu
```

is incorrect.

`cpu` is not a shell command.

Use:

```bash
kubectl describe pod rabbit | grep -i cpu
```

---

# Error 3 – Searching for `describe`

This command:

```bash
kubectl describe pod elephant | grep describe
```

will generally not help because `describe` is the command being executed, not necessarily text contained in the output.

Instead use:

```bash
kubectl describe pod elephant
```

or search for a specific field:

```bash
kubectl describe pod elephant | grep -i "last state"
```

---

# Error 4 – Editing a Pod Without Understanding Immutability

Some Pod fields cannot be changed after the Pod has been created.

If Kubernetes rejects your modification, recreate the Pod.

A common approach is:

```bash
kubectl delete pod elephant
kubectl create -f elephant.yaml
```

or, in a lab environment:

```bash
kubectl replace -f elephant.yaml --force
```

---

# Error 5 – Changing More Than Required

If the question says:

> Do not modify anything other than the required fields.

Do not regenerate the entire YAML manually.

Instead:

```bash
kubectl get pod elephant -o yaml > elephant.yaml
```

Then change only:

```yaml
resources:
  limits:
    memory: 20Mi
```

This preserves the existing configuration as much as possible.

---

# Error 6 – `CrashLoopBackOff` Is Not the Root Cause

Do not simply answer:

```text
CrashLoopBackOff
```

when asked:

> What is the Last State Reason?

Instead inspect:

```bash
kubectl describe pod elephant
```

You may find:

```text
State:          Waiting
Reason:         CrashLoopBackOff

Last State:
  Terminated
  Reason:       OOMKilled
```

Therefore:

```text
Current state reason = CrashLoopBackOff
Last state reason    = OOMKilled
```

This distinction is important.

# 22. Real-World Example

Imagine an application that normally requires:

```text
10Mi memory
```

but the Kubernetes Pod has:

```yaml
resources:
  limits:
    memory: 5Mi
```

The application starts:

```text
Memory usage = 2Mi
```

Everything is fine.

Later:

```text
Memory usage = 8Mi
```

The container exceeds the limit.

Kubernetes terminates it:

```text
OOMKilled
```

The controller/runtime restarts it.

The same thing happens again.

Eventually you may see:

```text
CrashLoopBackOff
```

The correct solution is not to blindly restart the Pod.

Instead:

1. Identify the failure.
2. Check the resource limit.
3. Determine the application's actual requirement.
4. Set an appropriate memory limit.
5. Recreate/redeploy the Pod if necessary.
6. Verify that the Pod reaches `Running`.

# 24. Interview Questions

## Q1. What is a CPU request in Kubernetes?

A CPU request tells the Kubernetes scheduler how much CPU the container requires for scheduling purposes.

Example:

```yaml
resources:
  requests:
    cpu: "100m"
```

---

## Q2. What is a CPU limit?

A CPU limit defines the maximum CPU a container can consume.

Example:

```yaml
resources:
  limits:
    cpu: "500m"
```

---

## Q3. What happens when a container exceeds its memory limit?

The container can be terminated due to an out-of-memory condition.

The Pod may show:

```text
Reason: OOMKilled
```

---

## Q4. What does OOMKilled mean?

`OOMKilled` means:

> Out Of Memory — the container was killed because it exceeded its available memory limit.

---

## Q5. What is CrashLoopBackOff?

`CrashLoopBackOff` means Kubernetes is repeatedly restarting a container that keeps failing and is backing off between restart attempts.

It describes the **current restart behavior**, not necessarily the original root cause.

---

## Q6. How do you find why a Pod is crashing?

Use:

```bash
kubectl describe pod <pod-name>
```

Then inspect:

```text
State
Last State
Reason
Events
```

Also check logs:

```bash
kubectl logs <pod-name>
```

and previous container logs:

```bash
kubectl logs <pod-name> --previous
```

---

## Q7. What is the difference between `State` and `Last State`?

`State` represents the current container state.

`Last State` represents the state of the previous container instance.

Example:

```text
State:
  Waiting
  Reason: CrashLoopBackOff

Last State:
  Terminated
  Reason: OOMKilled
```

---

## Q8. What does `kubectl describe` provide?

It provides detailed information about a Kubernetes resource, including:

* Configuration
* Conditions
* Container states
* Resource requests
* Resource limits
* Volumes
* Events
* Scheduling information
* Failure reasons

---

## Q9. Why might a Pod need to be deleted and recreated?

Some Pod specifications are immutable after creation.

If a field cannot be changed directly, the Pod may need to be recreated with the desired configuration.

---

## Q10. What is the difference between `kubectl delete` and `kubectl replace --force`?

### Delete

```bash
kubectl delete pod elephant
```

Deletes the Pod.

### Replace with Force

```bash
kubectl replace -f elephant.yaml --force
```

Forces replacement by deleting and recreating the resource from the YAML.

# 27. Final Takeaways

For this exercise, remember these core Kubernetes concepts:

1. **CPU requests** influence Pod scheduling.
2. **CPU limits** control maximum CPU consumption.
3. **Memory limits** can result in `OOMKilled` when exceeded.
4. `CrashLoopBackOff` indicates repeated container failures and restarts.
5. `Last State Reason` helps identify the actual previous container failure.
6. `kubectl describe pod` is one of the most important troubleshooting commands.
7. `kubectl logs --previous` is extremely useful for containers that keep crashing.
8. Some Pod fields cannot be modified after creation and may require recreation.
9. Always verify the final Pod state with:

```bash
kubectl get pod <pod-name>
```

10. In real-world troubleshooting, don't just restart a failing Pod — **find the reason first**.
