## 1. What is a DaemonSet?

### Question

**What is a DaemonSet in Kubernetes?**

### Explanation

A **DaemonSet** is a Kubernetes workload object that ensures that a copy of a Pod runs on **every node** or on **selected nodes** in the cluster.

For example, if you have:

```text
3 Worker Nodes
     │
     ├── Node 1 → DaemonSet Pod
     ├── Node 2 → DaemonSet Pod
     └── Node 3 → DaemonSet Pod
```

If a new node is added:

```text
4 Worker Nodes
     │
     ├── Node 1 → DaemonSet Pod
     ├── Node 2 → DaemonSet Pod
     ├── Node 3 → DaemonSet Pod
     └── Node 4 → DaemonSet Pod ← Automatically created
```

Similarly, if a node is removed, the DaemonSet Pod associated with that node is also removed.

### Common Use Cases

DaemonSets are commonly used for:

| Use Case             | Example                    |
| -------------------- | -------------------------- |
| Logging              | Fluentd, Fluent Bit        |
| Monitoring           | Node Exporter              |
| Networking           | kube-proxy                 |
| Container Networking | Flannel                    |
| Security Agents      | Node security agents       |
| Storage              | Node-level storage plugins |

### Real-World Example

Suppose you want to collect logs from every Kubernetes node.

Instead of manually creating a logging Pod on every node, you can create a DaemonSet:

```text
Node 1 → Fluentd
Node 2 → Fluentd
Node 3 → Fluentd
Node 4 → Fluentd
```

The DaemonSet automatically maintains one Pod per eligible node.

# 2. DaemonSet vs Deployment

This is a very important interview question.

| Feature        | Deployment                                  | DaemonSet                         |
| -------------- | ------------------------------------------- | --------------------------------- |
| Main purpose   | Run application replicas                    | Run Pod on nodes                  |
| Pod placement  | Scheduler decides                           | Usually one Pod per eligible node |
| Replicas       | User specifies replicas                     | Based on eligible nodes           |
| New node added | No automatic Pod unless replicas require it | Automatically creates Pod         |
| Common use     | Web application                             | Logging/monitoring agents         |
| Example        | NGINX                                       | Fluentd                           |

### Deployment

```text
3 replicas

Node 1 → Pod
Node 2 → Pod
Node 3 → Pod
```

The important thing is **3 Pods**, not necessarily one per node.

### DaemonSet

```text
3 nodes

Node 1 → Pod
Node 2 → Pod
Node 3 → Pod
```

The important thing is **one Pod per eligible node**.

# 3. How many DaemonSets are created in the cluster in all namespaces?

### Question

**How many DaemonSets are created in the cluster in all namespaces?**

### Command

```bash
kubectl get daemonsets --all-namespaces
```

Short form:

```bash
kubectl get ds -A
```

### Explanation

By default:

```bash
kubectl get daemonsets
```

shows DaemonSets only from the **current namespace**.

To check DaemonSets across **all namespaces**, use:

```bash
kubectl get daemonsets --all-namespaces
```

or:

```bash
kubectl get ds -A
```

### Sample Output

```text
NAMESPACE      NAME              DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR
kube-flannel   kube-flannel-ds   3         3         3       3            3           <none>
kube-system    kube-proxy        3         3         3       3            3           <none>
```

Here we have:

```text
2 DaemonSets
```

### Count Only

If you want only the number:

```bash
kubectl get ds -A --no-headers | wc -l
```

Example:

```text
2
```

### Important Notes

* `-A` means `--all-namespaces`.
* `ds` is short for `daemonsets`.
* `--no-headers` removes the table header.
* `wc -l` counts the number of lines.

### Interview Point

> To list DaemonSets across all namespaces, use `kubectl get ds -A`.

# 7. What is the image used by the Pod deployed by kube-flannel-ds?

### Question

**What is the image used by the Pod deployed by the `kube-flannel-ds` DaemonSet?**

### Command

```bash
kubectl describe daemonset kube-flannel-ds -n kube-flannel
```

Look for:

```text
Image:
```

### Easier Command

```bash
kubectl describe daemonset kube-flannel-ds -n kube-flannel | grep Image
```

Example:

```text
Image: registry.k8s.io/flannel/flannel:v0.x.x
```

> The exact image/version can vary depending on the Kubernetes environment.

### Another Method

You can inspect the DaemonSet YAML:

```bash
kubectl get daemonset kube-flannel-ds -n kube-flannel -o yaml
```

Then search for:

```yaml
image:
```

### JSONPath Method

A cleaner method is:

```bash
kubectl get daemonset kube-flannel-ds \
  -n kube-flannel \
  -o jsonpath='{.spec.template.spec.containers[*].image}'
```

### Important Notes

Your original command:

```bash
kubectl describe daemonset kube-flannel-ds --namespace=kube-flannel | grep image
```

may not return the expected result because Kubernetes output commonly displays the field as:

```text
Image:
```

Using:

```bash
grep Image
```

is safer:

```bash
kubectl describe daemonset kube-flannel-ds -n kube-flannel | grep Image
```

Linux `grep` is case-sensitive by default.

# 14. Why are selector and labels important?

A DaemonSet uses the selector to identify the Pods that belong to it.

We have:

```yaml
selector:
  matchLabels:
    app: elasticsearch
```

and:

```yaml
template:
  metadata:
    labels:
      app: elasticsearch
```

They match:

```text
app: elasticsearch
       ↓
Selector
       ↓
Pod Label
```

If these don't match, Kubernetes will reject the DaemonSet.

### Example of Incorrect Configuration

```yaml
selector:
  matchLabels:
    app: elasticsearch

template:
  metadata:
    labels:
      app: fluentd
```

This is incorrect because:

```text
elasticsearch != fluentd
```

# 15. Understanding the DaemonSet Status Columns

Run:

```bash
kubectl get ds -n kube-system
```

Example:

```text
NAME           DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE
elasticsearch  3         3         3       3            3
```

### Meaning

| Column     | Meaning                                    |
| ---------- | ------------------------------------------ |
| DESIRED    | Number of nodes where DaemonSet wants Pods |
| CURRENT    | Number of Pods currently created           |
| READY      | Number of ready Pods                       |
| UP-TO-DATE | Pods updated to the latest configuration   |
| AVAILABLE  | Pods currently available                   |

### Healthy Example

```text
DESIRED   CURRENT   READY
3         3         3
```

This generally means the DaemonSet is healthy.

### Problem Example

```text
DESIRED   CURRENT   READY
3         3         2
```

This means:

```text
3 Pods are expected
3 Pods exist
Only 2 Pods are ready
```

You should investigate the unhealthy Pod.

# 16. What happens when a new node is added?

Suppose the cluster currently has:

```text
Node 1
Node 2
Node 3
```

DaemonSet:

```text
Fluentd
```

Pods:

```text
Node 1 → Fluentd
Node 2 → Fluentd
Node 3 → Fluentd
```

Now add:

```text
Node 4
```

Kubernetes automatically creates:

```text
Node 4 → Fluentd
```

Therefore:

```text
3 nodes → 3 DaemonSet Pods

4 nodes → 4 DaemonSet Pods
```

This is one of the most important characteristics of a DaemonSet.

# 17. What happens when a node is removed?

Suppose:

```text
Node 1 → Fluentd
Node 2 → Fluentd
Node 3 → Fluentd
```

Node 3 is removed.

The DaemonSet will no longer maintain a Pod for Node 3.

Now:

```text
Node 1 → Fluentd
Node 2 → Fluentd
```

The number of DaemonSet Pods adjusts according to the eligible nodes.

# 18. Can a DaemonSet run on selected nodes?

### Yes.

By default, a DaemonSet targets eligible nodes.

You can restrict it using:

* `nodeSelector`
* Node affinity
* Taints and tolerations

### Example: nodeSelector

```yaml
spec:
  template:
    spec:
      nodeSelector:
        disk: ssd
```

Only nodes with:

```text
disk=ssd
```

will be eligible.

# 19. DaemonSet with Node Selector

Example:

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: logging-agent
spec:
  selector:
    matchLabels:
      app: logging-agent
  template:
    metadata:
      labels:
        app: logging-agent
    spec:
      nodeSelector:
        logging: enabled
      containers:
        - name: fluentd
          image: fluent/fluentd
```

Label a node:

```bash
kubectl label node node01 logging=enabled
```

Now the DaemonSet can schedule its Pod on that node.

# 20. Important Difference: DaemonSet and ReplicaSet

### ReplicaSet

ReplicaSet focuses on maintaining a specific number of Pods.

Example:

```yaml
replicas: 3
```

It wants:

```text
3 Pods
```

It doesn't matter whether they are distributed one per node.

### DaemonSet

DaemonSet focuses on node coverage.

If there are:

```text
5 eligible nodes
```

the DaemonSet generally wants:

```text
5 Pods
```

### Interview Answer

> **ReplicaSet manages the number of Pod replicas, whereas DaemonSet ensures that Pods run on each eligible node.**

# 22. Common Errors

## Error 1: Wrong YAML indentation

Kubernetes YAML is indentation-sensitive.

Incorrect:

```yaml
spec:
selector:
matchLabels:
```

Correct:

```yaml
spec:
  selector:
    matchLabels:
```

---

## Error 2: Selector does not match Pod labels

Incorrect:

```yaml
selector:
  matchLabels:
    app: elasticsearch

template:
  metadata:
    labels:
      app: fluentd
```

Correct:

```yaml
selector:
  matchLabels:
    app: elasticsearch

template:
  metadata:
    labels:
      app: elasticsearch
```

---

## Error 3: File name typo

In the command history:

```bash
touch fludentd.yaml
```

and:

```bash
kubectl apply -f fludentd.yaml
```

There is a typo:

```text
fludentd
```

The intended filename is:

```text
fluentd.yaml
```

Use:

```bash
touch fluentd.yaml
```

Then:

```bash
vi fluentd.yaml
```

And:

```bash
kubectl apply -f fluentd.yaml
```

### Important

The filename itself does not matter to Kubernetes.

Both can technically work:

```text
fluentd.yaml
fludentd.yaml
```

What matters is that you use the **same filename** when creating/editing and applying it.

```text
ImagePullBackOff
```

or:

```text
ErrImagePull
```

Check:

```bash
kubectl get pods -n kube-system
```

Then:

```bash
kubectl describe pod <pod-name> -n kube-system
```

* Incorrect image name
* Incorrect image tag
* Registry unavailable
* Node cannot access registry

# 25. Error: Pod Not Running on Every Node

If you expect:

```text
3 nodes → 3 Pods
```

but see fewer Pods, check:

```bash
kubectl get ds -A
```

Then:

```bash
kubectl describe ds <daemonset-name> -n <namespace>
```

Also check:

```bash
kubectl get nodes
```

Possible reasons include:

* Node is not Ready
* Node has taints
* DaemonSet has toleration requirements
* Node selector doesn't match
* Node affinity doesn't match
* Pod cannot be scheduled
* Image cannot be pulled

### Most Important Concepts

* DaemonSet is a Kubernetes workload.
* It is used for node-level applications.
* It normally maintains one Pod per eligible node.
* It automatically handles new eligible nodes.
* `kube-proxy` is commonly deployed as a DaemonSet.
* Logging and monitoring agents are common DaemonSet use cases.
* `nodeSelector`, node affinity, taints, and tolerations can affect where DaemonSet Pods run.
* DaemonSets do not normally use `replicas`.
* The selector and Pod template labels must match.
* `kubectl get ds -A` is the key command for checking DaemonSets across all namespaces.

# Final Interview Summary

> **DaemonSet = Node-level Pod manager**

If you remember only one thing:

```text
Deployment → I want N Pods

DaemonSet → I want a Pod on every eligible node
```

Example:

```text
3 eligible nodes
      ↓
DaemonSet
      ↓
3 Pods

Add another eligible node
      ↓
DaemonSet
      ↓
4 Pods
```

This makes DaemonSets ideal for **Fluentd, Fluent Bit, monitoring agents, kube-proxy, networking components, and other node-level services**.
