# Kubernetes Concepts

Before starting the lab, understand these important concepts.

| Concept | Description |
|----------|-------------|
| Node | A machine (VM or Physical Server) where Pods run |
| Control Plane | Manages the Kubernetes cluster |
| Worker Node | Runs application Pods |
| Pod | Smallest deployable unit in Kubernetes |
| Scheduler | Decides on which node a Pod should run |
| Taint | Prevents Pods from being scheduled on a node |
| Toleration | Allows a Pod to tolerate a taint and run on that node |

# Question 2

## Do any taints exist on node01?

---

## Command

```bash
kubectl describe node node01 | grep -i taints
```

---

## Explanation

This command displays the taints configured on **node01**.

If no taints exist, Kubernetes allows Pods to be scheduled normally.

---

## Sample Output (No Taints)

```text
Taints: <none>
```

---

## Sample Output (With Taint)

```text
Taints: spray=mortein:NoSchedule
```

---

## Kubernetes Concept

A **taint** tells Kubernetes:

> "Do NOT schedule Pods here unless they explicitly tolerate this taint."

---

## Important Notes

Taints have three effects:

| Effect | Meaning |
|----------|---------|
| NoSchedule | Do not schedule new Pods |
| PreferNoSchedule | Avoid scheduling if possible |
| NoExecute | Remove existing Pods and block new Pods |

# Question 3

## Create a taint on node01

**Key:** spray

**Value:** mortein

**Effect:** NoSchedule

---

## Command

```bash
kubectl taint nodes node01 spray=mortein:NoSchedule
```

---

## Explanation

This adds a taint to **node01**.

Now Kubernetes scheduler will refuse to place Pods on node01 unless they have a matching toleration.

---

## Sample Output

```text
node/node01 tainted
```

---

## Verify

```bash
kubectl describe node node01 | grep -i taints
```

Output

```text
Taints: spray=mortein:NoSchedule
```

---

## Real-World Example

Imagine a server dedicated for GPU workloads.

You don't want normal applications to run there.

Add a taint:

```
gpu=true:NoSchedule
```

Only AI workloads having the matching toleration will run there.

# Question 6

## Why is the Pod in Pending state?

---

## Explanation

At this point:

### node01

```
spray=mortein:NoSchedule
```

This blocks scheduling.

---

### controlplane

Already has the default taint:

```
node-role.kubernetes.io/control-plane:NoSchedule
```

Therefore:

- node01 rejects the Pod.
- controlplane rejects the Pod.

No node is available.

---

## Verify

```bash
kubectl describe pod mosquito
```

---

## Sample Output

```text

0/2 nodes are available:

1 node had untolerated taint

```

## Interview Question

**Q:** Does a taint stop Pod creation?

**Answer:**

No.

# Question 7

## Create another Pod named bee with a toleration

---

## YAML

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: bee

spec:
  containers:
    - name: bee
      image: nginx

  tolerations:
    - key: spray
      operator: Equal
      value: mortein
      effect: NoSchedule
```

---

## Command

```bash
kubectl create -f bee.yaml
```

---

## Explanation

This Pod has a toleration matching the taint on node01.

Therefore Kubernetes scheduler is allowed to place this Pod on node01.

---

## Sample Output

```text
pod/bee created
```

---

## Verify

```bash
kubectl get pods -o wide
```

Output

```text
NAME       READY   STATUS    NODE
bee        1/1     Running   node01
mosquito   0/1     Pending   <none>
```

---

## Kubernetes Concept

**Taint**

```
Node says:

I do not accept Pods.
```

---

**Toleration**

```
Pod says:

I know about your restriction.
You may schedule me.
```

---

## Important Note

A **toleration does not force** scheduling onto a node.

It only **permits** scheduling if the scheduler chooses that node.

# Question 9

## Remove the taint from the controlplane node

---

## Command

```bash
kubectl taint nodes controlplane node-role.kubernetes.io/control-plane:NoSchedule-
```

---

## Explanation

The trailing **-** removes the taint.

After removal, normal Pods can be scheduled on the control plane.

---

## Sample Output

```text
node/controlplane untainted
```

---

## Verify

```bash
kubectl describe node controlplane | grep -i taints
```

Output

```text
Taints: <none>
```

---

## Important Notes

Removing the control plane taint is common in:

- Minikube
- Kind
- Kubeadm practice clusters
- Home labs

Production clusters usually keep this taint.

# Taints vs Tolerations

| Taints | Tolerations |
|---------|-------------|
| Applied on Nodes | Applied on Pods |
| Prevent scheduling | Allow scheduling |
| Configured by Admin | Configured in Pod YAML |
| Protect Nodes | Permit access to protected nodes |

# Interview Questions

### Q1. What is a taint?

A taint is a restriction applied to a node that prevents Pods from being scheduled unless they have a matching toleration.

---

### Q2. What is a toleration?

A toleration is a Pod configuration that allows it to be scheduled onto a node with a matching taint.

---

### Q3. Does a toleration guarantee scheduling?

No. It only allows scheduling. The Kubernetes scheduler still decides the best node based on all scheduling rules.

---

### Q4. Can multiple taints exist on one node?

Yes. A node can have multiple taints, and a Pod may need multiple matching tolerations to be scheduled.

---

### Q5. What are the three taint effects?

- **NoSchedule** – Prevents new Pods from being scheduled.
- **PreferNoSchedule** – Tries to avoid scheduling, but not guaranteed.
- **NoExecute** – Evicts existing Pods without matching tolerations and blocks new Pods.

---

# Key Takeaways

- Pods are scheduled by the Kubernetes Scheduler.
- Taints protect nodes from unwanted workloads.
- Tolerations allow Pods to run on tainted nodes.
- A Pod in **Pending** often indicates a scheduling issue.
- The control plane node is tainted by default in most Kubernetes clusters.
- Removing a taint makes the node eligible for scheduling new Pods.
- Taints and tolerations are commonly used to dedicate nodes for specific workloads such as GPUs, databases, or system components.
