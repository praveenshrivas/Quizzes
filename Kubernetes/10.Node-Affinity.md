# 1. Check Labels on a Node

## Question

> How many Labels exist on node `node01`?

## Command

```bash
kubectl describe node node01
```

You can also use:

```bash
kubectl get node node01 --show-labels
```

## Explanation

Kubernetes nodes can have **labels** attached to them.

Labels are key-value pairs used to identify and select Kubernetes objects.

Example:

```text
Labels:
  beta.kubernetes.io/arch=amd64
  beta.kubernetes.io/os=linux
  kubernetes.io/hostname=node01
  color=blue
```

The exact number of labels depends on the current cluster configuration.

To inspect all labels:

```bash
kubectl get node node01 --show-labels
```

Example output:

```text
NAME     STATUS   ROLES    AGE   VERSION   LABELS
node01   Ready    <none>   ...   ...       beta.kubernetes.io/arch=amd64,...
```

You can also inspect only the labels section:

```bash
kubectl describe node node01
```

Look for:

```text
Labels:
```

## Important Notes

* Labels belong to Kubernetes objects.
* Nodes commonly have automatically assigned labels.
* You can add your own custom labels.
* Labels are frequently used with:

  * Node Selectors
  * Node Affinity
  * Services
  * Deployments
  * Scheduling rules

# 2. Check the Value of a Node Label

## Question

> What is the value set to the label key `beta.kubernetes.io/arch` on `node01`?

## Command

```bash
kubectl get node node01 --show-labels
```

Look for:

```text
beta.kubernetes.io/arch=amd64
```

Therefore:

```text
Key   = beta.kubernetes.io/arch
Value = amd64
```

You can retrieve the value directly using JSONPath:

```bash
kubectl get node node01 -o jsonpath='{.metadata.labels.beta\.kubernetes\.io/arch}'
```

Expected output:

```text
amd64
```

## Explanation

A Kubernetes label consists of:

```text
KEY=VALUE
```

For example:

```text
beta.kubernetes.io/arch=amd64
```

Here:

| Component | Value                     |
| --------- | ------------------------- |
| Key       | `beta.kubernetes.io/arch` |
| Value     | `amd64`                   |

The `.` characters need to be escaped when using JSONPath:

```text
beta\.kubernetes\.io/arch
```

## Important Note

`beta.kubernetes.io/arch` is an older label name.

Modern Kubernetes generally uses:

```text
kubernetes.io/arch
```

For example:

```text
kubernetes.io/arch=amd64
```

# 3. Apply a Label to a Node

## Question

> Apply a label `color=blue` to node `node01`.

## Command

```bash
kubectl label node node01 color=blue
```

Expected output:

```text
node/node01 labeled
```

Verify:

```bash
kubectl get nodes --show-labels
```

Or:

```bash
kubectl describe node node01
```

You should see:

```text
Labels:
  color=blue
```

## Explanation

The command follows this structure:

```bash
kubectl label node <node-name> <key>=<value>
```

Example:

```bash
kubectl label node node01 color=blue
```

This creates:

```text
color=blue
```

on:

```text
node01
```

## If the Label Already Exists

You may get an error such as:

```text
error: 'color' already has a value (red), and --overwrite is false
```

In that case:

```bash
kubectl label node node01 color=blue --overwrite
```

## Important Notes

Labels are not the same thing as taints.

### Label

A label helps Kubernetes **select** a node.

```text
color=blue
```

### Taint

A taint can **prevent pods from being scheduled** on a node unless the pod tolerates the taint.

# 5. Check Which Nodes Can Run the Blue Pods

## Question

> Which nodes can the Pods for the `blue` Deployment be placed on?

> Make sure to check taints on both nodes.

## Step 1 – Check Nodes

```bash
kubectl get nodes
```

Example:

```text
NAME           STATUS   ROLES           AGE   VERSION
controlplane   Ready    control-plane   ...   ...
node01         Ready    <none>          ...   ...
```

---

## Step 2 – Check Taints on Control Plane

```bash
kubectl describe node controlplane | grep -i taints
```

Example:

```text
Taints: node-role.kubernetes.io/control-plane:NoSchedule
```

---

## Step 3 – Check Taints on node01

```bash
kubectl describe node node01 | grep -i taints
```

If there are no taints:

```text
Taints:             <none>
```

---

## Understanding the Result

Suppose:

```text
controlplane
Taints:
node-role.kubernetes.io/control-plane:NoSchedule
```

and:

```text
node01
Taints:
<none>
```

Then a normal Pod without a matching toleration **cannot normally be scheduled on the control plane**.

Therefore:

```text
blue Pods → node01
```

assuming `node01` is otherwise schedulable.

# 6. Set Node Affinity for Blue Deployment

## Question

> Set Node Affinity to the `blue` Deployment to place the Pods on `node01` only.

Requirements:

```text
Node label:
color=blue
```

Use:

```text
requiredDuringSchedulingIgnoredDuringExecution
```

Key:

```text
color
```

Value:

```text
blue
```

---

## Step 1 – Make Sure node01 Has the Label

```bash
kubectl label node node01 color=blue
```

If already present:

```bash
kubectl label node node01 color=blue --overwrite
```

Verify:

```bash
kubectl get node node01 --show-labels
```

---

## Step 2 – Edit the Deployment

```bash
kubectl edit deployment blue
```

Add the following under:

```yaml
spec:
  template:
    spec:
```

### Node Affinity YAML

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: color
              operator: In
              values:
                - blue
```

The Deployment will look approximately like:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: blue
spec:
  replicas: 3
  selector:
    matchLabels:
      app: blue
  template:
    metadata:
      labels:
        app: blue
    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: color
                    operator: In
                    values:
                      - blue
      containers:
        - name: nginx
          image: nginx
```

---

## What Does This Mean?

This rule:

```yaml
requiredDuringSchedulingIgnoredDuringExecution:
```

means:

> The Pod **must** be scheduled onto a node satisfying the affinity rule.

The condition is:

```text
color=blue
```

Therefore Kubernetes looks for nodes having:

```text
color=blue
```

Since:

```text
node01 → color=blue
```

the Pods can be scheduled on:

```text
node01
```

```bash

```

You should find the affinity configuration.

You can also use:

```bash
kubectl get deployment blue -o yaml
```

Search for:

```yaml

```

---

## Important Concept

There is an important difference between:

```text
Before Node Affinity
```

and:

```text
After Node Affinity
```

### Before

Kubernetes scheduler can choose any suitable node.

```text
blue Pod
   |
   +---- node01
   |
   +---- controlplane
```

However, taints may prevent certain nodes.

### After

Node affinity explicitly requires:

```text
color=blue
```

So:

```text
blue Pod
   |
   +---- node01 (color=blue) ✓
   |
   +---- other nodes ✗
```

# 8. Create Red Deployment on Control Plane

## Question

> Create a new Deployment named `red` with the nginx image and 2 replicas.

Requirements:

* Deployment name: `red`
* Image: `nginx`
* Replicas: `2`
* Pods must run on the `controlplane` node.
* Use label:

```text
node-role.kubernetes.io/control-plane
```

* The label already exists on the control plane.
* Use node affinity.
* Use:

```text
requiredDuringSchedulingIgnoredDuringExecution
```

---

## YAML

Create:

```bash
vi reddeploy.yaml
```

Add:

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: red

spec:
  replicas: 2

  selector:
    matchLabels:
      run: nginx

  template:
    metadata:
      labels:
        run: nginx

    spec:
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: node-role.kubernetes.io/control-plane
                    operator: Exists

      containers:
        - name: nginx
          image: nginx
          imagePullPolicy: Always
```

---

## Create the Deployment

```bash
kubectl create -f reddeploy.yaml
```

Or:

```bash
kubectl apply -f reddeploy.yaml
```

Verify:

```bash
kubectl get deployment red
```

Expected:

```text
NAME   READY   UP-TO-DATE   AVAILABLE
red    2/2     2            2
```

---

# 9. Understanding the Red Deployment Affinity

The important part is:

```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: node-role.kubernetes.io/control-plane
              operator: Exists
```

---

## `key`

```yaml
key: node-role.kubernetes.io/control-plane
```

Kubernetes checks whether the node has this label.

---

## `operator: Exists`

```yaml
operator: Exists
```

means:

> The label key must exist. I don't care what its value is.

This is different from:

```yaml
operator: In
```

For example:

```yaml
operator: In
values:
  - blue
```

means:

```text
color must equal blue
```

Whereas:

```yaml
operator: Exists
```

means:

```text
The specified key simply needs to exist.
```

---

# 10. Important: Check the Control Plane Taint

Before expecting the `red` Pods to run on the control plane, check:

```bash
kubectl describe node controlplane | grep -i taints
```

If you see:

```text
Taints: node-role.kubernetes.io/control-plane:NoSchedule
```

then node affinity **alone is not enough**.

Why?

Because:

```text
Node Affinity → tells Kubernetes WHERE the Pod should go
```

but:

```text
Taint → tells Kubernetes WHICH Pods are allowed onto the node
```

Therefore, if the control plane has a `NoSchedule` taint, the Pod also needs a matching **toleration**.

---

## Red Deployment with Toleration

If your control plane is tainted with:

```text
node-role.kubernetes.io/control-plane:NoSchedule
```

use:

```yaml
apiVersion: apps/v1
kind: Deployment

metadata:
  name: red

spec:
  replicas: 2

  selector:
    matchLabels:
      run: nginx

  template:
    metadata:
      labels:
        run: nginx

    spec:

      tolerations:
        - key: "node-role.kubernetes.io/control-plane"
          operator: "Exists"
          effect: "NoSchedule"

      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: node-role.kubernetes.io/control-plane
                    operator: Exists

      containers:
        - name: nginx
          image: nginx
          imagePullPolicy: Always
```

Apply:

```bash
kubectl apply -f reddeploy.yaml
```

# 12. Node Labels vs Node Affinity vs Taints

This is one of the most important Kubernetes concepts for interviews.

| Feature       | Purpose                              |
| ------------- | ------------------------------------ |
| Label         | Identifies/selects an object         |
| Node Selector | Places Pods on nodes matching labels |
| Node Affinity | Advanced node selection rules        |
| Taint         | Prevents Pods from being scheduled   |
| Toleration    | Allows Pods to tolerate a taint      |
| Scheduler     | Decides where Pods should run        |

---

## Simple Real-World Example

Imagine a company has:

```text
node01 → High-performance server
node02 → General-purpose server
node03 → GPU server
```

Labels could be:

```text
node01 → hardware=high-performance
node02 → hardware=standard
node03 → hardware=gpu
```

A machine-learning Pod can request:

```yaml
nodeAffinity:
  requiredDuringSchedulingIgnoredDuringExecution:
    nodeSelectorTerms:
      - matchExpressions:
          - key: hardware
            operator: In
            values:
              - gpu
```

Kubernetes will then try to place the Pod on:

```text
node03
```

---

# 13. Node Affinity Types

There are two major types you should remember.

## 1. Required

```yaml
requiredDuringSchedulingIgnoredDuringExecution
```

Meaning:

> The rule is mandatory during scheduling.

If no node satisfies the rule:

```text
Pod remains Pending
```

---

## 2. Preferred

```yaml
preferredDuringSchedulingIgnoredDuringExecution
```

Meaning:

> Kubernetes prefers the matching node, but it is not mandatory.

If no matching node is available:

```text
Pod can still be scheduled elsewhere
```

---

## Interview Shortcut

Remember:

```text
required = MUST
preferred = TRY
```

---

# 14. Understanding `IgnoredDuringExecution`

Consider:

```yaml
requiredDuringSchedulingIgnoredDuringExecution
```

Break it into two parts:

### During Scheduling

```text
requiredDuringScheduling
```

The rule is checked when Kubernetes decides where to place the Pod.

### During Execution

```text
IgnoredDuringExecution
```

If the node's label later changes, Kubernetes does not automatically evict the already-running Pod simply because the affinity rule is no longer satisfied.

---

# 15. Node Affinity Operators

Common operators include:

| Operator       | Meaning                                       |
| -------------- | --------------------------------------------- |
| `In`           | Value must be one of the specified values     |
| `NotIn`        | Value must not be one of the specified values |
| `Exists`       | Label key must exist                          |
| `DoesNotExist` | Label key must not exist                      |
| `Gt`           | Greater than                                  |
| `Lt`           | Less than                                     |

---

## Example: `In`

```yaml
matchExpressions:
  - key: color
    operator: In
    values:
      - blue
```

Means:

```text
color must be blue
```

---

## Example: `Exists`

```yaml
matchExpressions:
  - key: node-role.kubernetes.io/control-plane
    operator: Exists
```

Means:

```text
The label key must exist.
```

The actual value doesn't matter.

# 16. Common Errors

## Error 1: Label Already Exists

Command:

```bash
kubectl label node node01 color=blue
```

Possible error:

```text
error: 'color' already has a value
```

### Solution

```bash
kubectl label node node01 color=blue --overwrite
```

---

# Error 2: Pod Stuck in Pending

Check:

```bash
kubectl get pods
```

If:

```text
STATUS
Pending
```

inspect the Pod:

```bash
kubectl describe pod <pod-name>
```

Look at the:

```text
Events:
```

section.

Common causes include:

* Node affinity doesn't match any node.
* Node is tainted.
* Pod doesn't have the required toleration.
* Node is NotReady.
* Insufficient CPU.
* Insufficient memory.

---

# Error 3: Affinity Matches No Nodes

For example:

```yaml
key: color
operator: In
values:
  - blue
```

but no node has:

```text
color=blue
```

Then the Pod cannot be scheduled.

Check:

```bash
kubectl get nodes --show-labels
```

Fix:

```bash
kubectl label node node01 color=blue
```

---

# Error 4: Control Plane Has a Taint

You may have:

```text
node-role.kubernetes.io/control-plane:NoSchedule
```

but only configured:

```yaml
nodeAffinity:
```

The Pod may remain:

```text
Pending
```

Check:

```bash
kubectl describe pod <pod-name>
```

If the problem is a taint, add the appropriate toleration.

---

# Error 5: Editing the Wrong Section

Node affinity belongs under:

```yaml
spec:
  template:
    spec:
```

Correct:

```yaml
spec:
  template:
    spec:
      affinity:
        nodeAffinity:
```

Not:

```yaml
spec:
  affinity:
```

for a Deployment Pod template.

Remember:

> A Deployment creates Pods, so Pod-level scheduling configuration belongs inside the Pod template.

# 20. Interview Questions

## Q1. What is a Kubernetes label?

A label is a key-value pair attached to Kubernetes objects for identification and selection.

Example:

```text
color=blue
```

---

## Q2. What is Node Affinity?

Node Affinity allows you to control which nodes a Pod can or should be scheduled on based on node labels.

---

## Q3. Difference between Node Selector and Node Affinity?

| Node Selector            | Node Affinity        |
| ------------------------ | -------------------- |
| Simple                   | More powerful        |
| Basic key-value matching | Supports expressions |
| Limited flexibility      | Supports operators   |
| Easier to configure      | More flexible        |

---

## Q4. What does `requiredDuringSchedulingIgnoredDuringExecution` mean?

It means the scheduling condition is mandatory when the Pod is initially scheduled, but changes to the node's labels after scheduling do not automatically cause the Pod to be evicted.

---

## Q5. What does `operator: In` mean?

The node label value must be one of the values specified in:

```yaml
values:
```

Example:

```yaml
operator: In
values:
  - blue
```

---

## Q6. What does `operator: Exists` mean?

It checks whether a particular label key exists.

Example:

```yaml
key: node-role.kubernetes.io/control-plane
operator: Exists
```

The value of the label is not important.

---

## Q7. What is a taint?

A taint prevents Pods from being scheduled on a node unless the Pod has a matching toleration.

---

## Q8. What is a toleration?

A toleration allows a Pod to be scheduled onto a node that has a matching taint.

---

## Q9. Is a toleration enough to force a Pod onto a node?

**No.**

A toleration only says:

> "This Pod is allowed to run on this tainted node."

It does not say:

> "This Pod must run on this node."

To force/select a node, use:

* Node Selector
* Node Affinity

---

## Q10. What is the difference between taint and node affinity?

### Node Affinity

```text
Pod → I WANT this type of node
```

### Taint

```text
Node → I DON'T WANT certain Pods
```

### Toleration

```text
Pod → I AM ALLOWED on that tainted node
```

A useful interview memory trick:

```text
Affinity = Pod chooses Node
Taint = Node rejects Pod
Toleration = Pod is allowed despite Taint
```

And remember the three important scheduling concepts:

```text
LABEL
  ↓
Identifies/selects nodes

NODE AFFINITY
  ↓
Controls where Pods should/must be scheduled

TAINT + TOLERATION
  ↓
Controls which Pods are allowed onto a node
```

### Most Important Interview Formula

```text
Node Label
     ↓
Node Affinity
     ↓
Pod chooses suitable node
```

and:

```text
Node Taint
     ↓
Toleration
     ↓
Pod is allowed onto the node
```

Together, these concepts form a major part of **Kubernetes Pod Scheduling**.
